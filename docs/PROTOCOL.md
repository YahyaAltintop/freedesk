# Protocol Contract (Wire Contract)

This document defines the contract that must be followed exactly between the **Frontend (Viewer)** and the **Host Agent**:
1. The shape, ordering and cleanup of the Realtime Database nodes used for discovery, requests and WebRTC signaling.
2. The format of the input (mouse/keyboard) messages sent over the DataChannel after the connection is established.

Both sides are coded against this document. **If this contract changes, both sides must be updated together.**

---

## 1. Realtime Database

### 1.1 Nodes
```
/hosts/{code}
/inbox/{ownerUid}/{sessionId}
/sessions/{sessionId}
```
`code` is the host's 9-digit pairing code; `sessionId` is a push key generated by the viewer and is the **same** under `/inbox` and `/sessions`.

### 1.2 Schema
| Path | Writer | Type | Description |
|-----|-------|-----|----------|
| `/hosts/{code}/ownerUid` | host | string | The agent's uid for this run (must equal the writer) |
| `/hosts/{code}/name` | host | string | Display name, 1–64 chars |
| `/hosts/{code}/version` | host | string | Agent version |
| `/hosts/{code}/lastSeen` | host | number | `ServerValue.TIMESTAMP`; refreshed every 30 s |
| `/inbox/{owner}/{id}/viewerUid` | viewer | string | Must equal the writer |
| `/inbox/{owner}/{id}/code` | viewer | string | The code that was entered |
| `/inbox/{owner}/{id}/createdAt` | viewer | number | `ServerValue.TIMESTAMP` |
| `/sessions/{id}/viewerUid` | viewer | string | Immutable; must equal the creator |
| `/sessions/{id}/ownerUid` | viewer | string | Immutable; copied from `/hosts/{code}` |
| `/sessions/{id}/status` | both | string | `waiting` → `connecting` → `connected` → `ended` |
| `/sessions/{id}/createdAt` | viewer | number | `ServerValue.TIMESTAMP`, immutable |
| `/sessions/{id}/offer` | host | `{ type, sdp }` | SDP offer (`type` = `"offer"`) |
| `/sessions/{id}/answer` | viewer | `{ type, sdp }` | SDP answer (`type` = `"answer"`) |
| `/sessions/{id}/hostCandidates/{pushId}` | host | `{ candidate, sdpMid, sdpMLineIndex, usernameFragment }` | The host's ICE candidates |
| `/sessions/{id}/viewerCandidates/{pushId}` | viewer | `{ candidate, sdpMid, sdpMLineIndex, usernameFragment }` | The viewer's ICE candidates |

The ICE candidate field names match the browser's `RTCIceCandidate` JSON output exactly; no conversion is needed. Timestamps are always the server placeholder (`serverTimestamp()` in the Web SDK, `{".sv":"timestamp"}` over REST); the rules reject client clocks.

### 1.3 Sequence
```
0.  host   : on start writes /hosts/{code}; heartbeats lastSeen every 30 s;
             streams /inbox/{ownerUid} (SSE)
1.  viewer : reads /hosts/{code}; treats lastSeen older than 90 s as offline
2.  viewer : arms onDisconnect().remove() on /sessions/{id} AND /inbox/{ownerUid}/{id}
3.  viewer : ONE atomic multi-path update creating
             /sessions/{id}  = { viewerUid, ownerUid, status: "waiting", createdAt }
             /inbox/{ownerUid}/{id} = { viewerUid, code, createdAt }
3a. viewer : listens on /sessions/{id} (status + offer arrive on the same node)
4.  host   : receives the inbox entry (push), deletes it immediately, opens ONE
             stream on /sessions/{id}; the initial snapshot must show
             viewerUid == entry.viewerUid, ownerUid == host uid, status == "waiting",
             otherwise the request is ignored
4a. host   : status = "connecting"; asks the operator (Yes/No window, 45 s).
             While asking, the host watches the same stream: the node disappearing
             or status becoming "ended" means the viewer withdrew → prompt closes.
             No/timeout → status = "ended", then /sessions/{id} is deleted
5.  host   : sets up the PeerConnection, adds the video track + DataChannel("input")
6.  host   : generates the OFFER → writes /sessions/{id}/offer
6a. host   : pushes its local ICE candidates to /hostCandidates
7.  viewer : receives the offer → setRemoteDescription
8.  viewer : generates the ANSWER → writes /sessions/{id}/answer
8a. viewer : pushes its local ICE candidates to /viewerCandidates
9.  host   : receives the answer (same stream) → setRemoteDescription
10. both sides: add the other side's candidates → connection established;
             both may write status = "connected"
11. end    : whoever ends it writes status = "ended" and deletes /sessions/{id}
             (and the inbox entry if still present). The other side observes
             either the status or the node vanishing. Deleting an already
             deleted node is allowed, so both sides may clean up.
```

### 1.4 Lifecycle states (`/sessions/{id}/status`)
`waiting` → `connecting` → `connected` → `ended`

- `connecting` is written the moment the host sees the request and also carries the meaning **awaiting operator approval**; in this state the viewer shows "Waiting for host approval…".
- An `ended` that arrives without a preceding `connected` is interpreted by the viewer as a **rejection**.
- **The node disappearing is equivalent to `ended`.** Because `/sessions/{id}` is readable only by its participants, a deleted node surfaces to attached listeners as a *cancelled/permission-denied read*, not as a `null` value; both sides must treat that as "gone".
- The host handles **one session at a time**: a request arriving while another is pending or active is answered with `ended` immediately.

### 1.5 Cleanup guarantees
| Situation | Who cleans up |
|-----------|---------------|
| Normal end (either side clicks disconnect / closes) | The ending side writes `ended` and deletes the node; the other side may delete again (no error) |
| Viewer tab closed or crashed | RTDB `onDisconnect` deletes `/sessions/{id}` and the inbox entry; the host sees the node vanish |
| Host agent exits gracefully | Finishes its session (`ended` + delete), deletes `/hosts/{code}`, deletes its anonymous account |
| Host agent killed | `/hosts/{code}` goes stale; viewers show it offline after 90 s and may delete it after 5 min; the viewer's `onDisconnect` still removes the session |
| Both die before step 2 armed | The session node stays until the 1 h rule allows any client that knows the id to delete it (nothing can list `/sessions`) |

## 2. DataChannel — Input Protocol

### 2.1 Channel
- **Label:** `input`
- **Opening side:** the host (offerer). The viewer receives it via `ondatachannel`.
- **Direction:** viewer → host (input events). The channel is technically bidirectional; in v1 only viewer→host is used.
- **Configuration:** `ordered: true` (reliable, ordered).
- **Encoding:** each event is a single **JSON text** frame (UTF-8).

> **Versioning:** this protocol is version **1**. When the channel opens, the client may send `{ "t": "hello", "v": 1 }` as the first message (the host may ignore it, but it is reserved for forward compatibility).

### 2.2 Message types
All messages contain a `t` (type) field. Coordinates are **normalized**: `x` and `y` are in the range `[0.0, 1.0]` relative to the captured screen frame (top-left is `0,0`).

| `t` | Meaning | Fields | Example |
|-----|-------|---------|-------|
| `m` | Mouse move | `x`, `y` | `{"t":"m","x":0.5123,"y":0.2240}` |
| `md` | Mouse button down | `b`, `x`, `y` | `{"t":"md","b":0,"x":0.51,"y":0.22}` |
| `mu` | Mouse button up | `b`, `x`, `y` | `{"t":"mu","b":0,"x":0.51,"y":0.22}` |
| `w` | Scroll (wheel) | `dx`, `dy` | `{"t":"w","dx":0,"dy":-120}` |
| `kd` | Key down | `code` | `{"t":"kd","code":"KeyA"}` |
| `ku` | Key up | `code` | `{"t":"ku","code":"KeyA"}` |
| `hello` | Handshake (opt.) | `v` | `{"t":"hello","v":1}` |

#### Mouse button codes (`b`)
| Value | Button |
|-------|-----|
| `0` | Left |
| `1` | Right |
| `2` | Middle |

#### Scroll (`w`)
- `dy`: vertical wheel delta. **Windows `WHEEL_DELTA` = 120** is the reference; one "tick" = `120`. Positive `dy` = up, negative `dy` = down (Windows `mouse_event` convention).
- `dx`: horizontal wheel delta (same scale). `0` if there is no horizontal scroll.
- The client converts the browser's `WheelEvent.deltaY` value to this scale.

#### Keyboard (`code`)
- `code` is the browser's [`KeyboardEvent.code`](https://developer.mozilla.org/docs/Web/API/KeyboardEvent/code) value (physical key; independent of keyboard layout), e.g. `"KeyA"`, `"Digit1"`, `"Enter"`, `"ShiftLeft"`, `"ArrowUp"`.
- **Modifier keys are separate events.** For example, for an uppercase `A`: `kd ShiftLeft` → `kd KeyA` → `ku KeyA` → `ku ShiftLeft`. There is no separate "modifiers" field; the host tracks key state from the events, just like a real keyboard.
- The host side maps `code` → Windows virtual key code.

### 2.3 Held-state rule (both sides)
Both peers remember what is currently pressed.
- The **viewer** sends `ku` for every held key (most recent first) and `mu` for every held button when its window loses focus, the page is hidden, control is switched off, or the page is torn down; it uses pointer capture so a button released outside the video still produces `mu`.
- The **host** releases everything it still holds when the DataChannel closes or the session ends, regardless of what the viewer managed to send.
A key or button must never remain pressed on the host after the viewer is gone.

### 2.4 Coordinate conversion (host side)
Normalized coordinates are an **exact** match for Windows `SendInput`:
```
absX = round(x * 65535)
absY = round(y * 65535)
// MOUSEEVENTF_ABSOLUTE | MOUSEEVENTF_MOVE
```
This lets the host position absolutely without knowing the screen resolution. Multi-monitor support is out of scope for v1 (the primary screen is assumed; the coordinates map to the primary display).

### 2.5 Design notes
- **Why normalized coordinates?** The viewer's window and the host's screen are at different resolutions; `[0,1]` makes both sides resolution-independent.
- **Why `code` (not key)?** Remote control requires physical key mapping; `code` is independent of keyboard layout and maps reliably to a virtual key.
- **Why a single reliable channel?** For v1, simplicity and correctness take priority. Later, a separate `ordered:false, maxRetransmits:0` (unreliable) channel for high-frequency `m` events could be considered as an optimization.
